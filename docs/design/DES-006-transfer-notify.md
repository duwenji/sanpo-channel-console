## 目的・背景

配信元が鍵をなくした・漏れたときに、運用者の本人確認を経て新しい鍵に移せるようにする（ADR-001 D-3・A-15、API-001 C-11）。あわせて、判定・取り下げ・移し替えの結果を配信元にメールで知らせる（ADR-001 A-19、API-001 C-14）。

## 方針・決定事項

| No. | 判断 | 理由 |
|---|---|---|
| J-1 | 3d は 1 つの PR にする | 開発者の決定（2026-10-04） |
| J-2 | 申し出は、最初の紐づけと同じ一度きりの文字列への署名で新しい鍵を示し、理由（`lost`/`leaked`/`other`）、利用者に見せる理由（60 文字まで）、運用者への説明を付ける。新しい鍵は `pending_transfer`、そのアカウントIDはこの時点で予約する | API-001。認められなくても、そのアカウントIDは再利用させない（DM-001 M-7） |
| J-3 | 本人確認の「鍵とは別の経路」の手順は今は決めず、運用者が確かめた方法と内容を記録する（両方必須） | 開発者の決定（2026-10-04）。ADR-001 未決事項 No.6 は運用の開始前に |
| J-4 | 承認は 1 つのトランザクションで、移し替え・配信元（新しいアカウントID、ロックを外す）・新旧の鍵・すべてのチャンネル・古い鍵の審査待ちの申請（`uploading`・`validating` を含む。→ `returned`）・操作の記録を書く。あとでアップロードを `archive/` に移し、公開を頼み、メールを頼む | DM-001。機械審査が後から来ても、`uploading` を条件に書くので記録は変わらない |
| J-5 | `publisherChange` は、承認のときに `from`（リストに載っている版の配信元）・`at`・`reason` を書き、新しい鍵で署名した最初の版の承認で `until`（90 日後）を書く。公開の Lambda は、`until` が過ぎておらず、`from` が載せる版の配信元と違うときだけ載せる | API-002 は「移し替え後の最初の版から 90 日」。古い版が載っている間に出すと `from` と `publisher` が同じになり V-16 に反する |
| J-6 | 運用者の一覧は、確認待ちを GSI2 `QUEUE#TRANSFER`（古い順）、それ以外を GSI1 `TRANSFERS`（新しい順、状態で絞る）から読む | 過去の申し出と本人確認の記録を見るため（DM-001 1.2） |
| J-7 | 退会すると、確認待ちの申し出は取り消しになり、新しい鍵は外れる | DM-001 の退会 |
| J-8 | メールは、状態を変えたトランザクションのあとに SQS に知らせを入れ、通知の Lambda が送る。キューに入れられなくても操作は成功させる（ログに残す） | ADR-001 A-19、API-001 C-14 |
| J-9 | 送る出来事は、承認・差し戻し・却下・取り下げ・移し替えの承認・認めない。本文は結果・理由（指摘、運用者のメッセージ）・画面へのリンクだけ。宛先は Cognito で確認済みのメールアドレス（`contact` ではない） | C-14。見本・運用者の ID・トークンは入れない |
| J-10 | 同じ知らせが 2 度届いても 1 通にするため、送ったら `NOTICE#{noticeId}`（30 日の TTL）と `notification.sent`（メッセージ ID）を書き、送る前に確かめる | SQS の標準キューは同じメッセージを 2 度届けることがある（CV-13） |
| J-11 | 3 回送れなければ、最後の試みで `notification.failed` を残し、メッセージはデッドレターキューへ。デッドレターキューに入ったら運用者の警報（SNS）。確認済みのアドレスがない・退会した配信元は、再送せず `notification.failed`（`no_verified_email`） | ADR-001 A-19 |
| J-12 | 送り方は環境の設定 `notify` で選ぶ。開発用は `log`（SES を呼ばず、件名と本文の長さだけをログに出す）。本番も、独自ドメイン（T-7）と SES のサンドボックスの解除（T-8）までは `log`。`ses` にすると、その送信元のドメインの ID と構成セットにだけ `ses:SendEmail` を許す | 開発者の決定（2026-10-04: 開発用は送らずに記録だけ） |
| J-13 | バウンス・苦情を SES の構成セットで受けて操作の記録に残すのは、本番でドメインを用意するとき（T-7・T-8） | 開発用は送らないため |

## 検証結果

| 項目 | 結果 |
|---|---|
| API のテスト | 移し替え 2 件: 申し出・`transfer_pending`・確認待ちの一覧・本人確認の必須・承認で新しい鍵に移り審査待ちを差し戻す・古い版が載っている間は `publisherChange` を出さない・新しい鍵の最初の版から 90 日出す、取り消し・認めない・過去の一覧。通知 2 件: 判定と取り下げで 1 件ずつ（運用者の ID を含まない）、キューが落ちても操作は成功 |
| 通知の Lambda のテスト | 4 件: 本文（指摘・メッセージ・リンク）、1 回だけ送り宛先を記録しない、最後の試みで失敗を記録、確認済みのアドレスがなければ送らない |
| CDK | 13 件（キューと再送 3 回・デッドレターキュー・警報・`log` のときは `ses:SendEmail` を許さない・`ses` のときは送信元のドメインだけ） |
| テストの総数 | ルート 106・web 9・infra 13 件合格、`tsc -b` 通過 |
| 本物の AWS での通しの確認（`tools/e2e/transfer.ts`） | 鍵 A で署名した版 1 を承認 → 配信元が鍵 B への移し替えを申し出て、運用者の一覧に出て、承認で鍵 B が使用中に → 鍵 B で署名した版 2 が機械審査に合格して承認 → リストに版 2・配信元 B・`publisherChange.from` が A で載り、準拠テストは V-07・V-16 を含めて全て合格。メールは版 1 の承認・移し替えの承認・版 2 の承認の 3 件が `notification.sent` として記録された（開発用なので送らない）。後片付けで Cognito の確認用のユーザーも消した |

## 未決事項・リスク

| No. | 内容 | 対応 |
|---|---|---|
| 1 | 本人確認の手順（ADR-001 未決事項 No.6） | 運用の開始前に、運用者の手順書で決める |
| 2 | 実際にメールを送るのは、独自ドメイン（T-7）・DKIM/SPF/DMARC・SES のサンドボックスの解除（T-8）・バウンスと苦情の受け取りの後 | 本番の準備で |
| 3 | 移し替えを承認したあと、`publisherChange` が載るのは新しい鍵の版が承認されてから。それまでのアプリは古い版を使い続ける | API-002 P-9 のとおり。漏れたときは運用者が取り下げを検討する（運用者の使い方に記載） |
| 4 | 送ったあと記録の書き込みに失敗すると、再送で 2 通になりうる | 起きにくく、害も小さいので受け入れる |
| 5 | DM-001 1.2 の補足（GSI1 `TRANSFERS`、`NOTICE`、`publisherChange.until` の数え方） | 開発者の承認 |
