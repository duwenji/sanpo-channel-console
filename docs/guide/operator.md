## 1. はじめてのログイン

運用者のアカウントは、開発・保守の担当者が作ります（自分では登録できません。[開発・保守ガイド](maintainer.md#7-運用者を足す外す)）。

1. 「Your temporary password」という件名のメールが Cognito から届きます（迷惑メールに入ることがあります）
2. 運用者の画面を開くと、ログインの画面に移ります。メールアドレスと仮のパスワードでログインします
3. 新しいパスワードを決めます（12 文字以上、大文字・小文字・数字・記号を含む）
4. 認証アプリ（Google Authenticator、Microsoft Authenticator など）で表示された QR コードを読み、6 桁のコードを入れて MFA を登録します
5. 運用者の画面が開きます。上に「開発用」と出ていれば開発用の環境です

- MFA はすべての利用者に必須です。認証アプリの入った端末をなくしたら、開発・保守の担当者に MFA の登録のやり直しを頼んでください
- 画面のログインは、ブラウザのタブを閉じると消えます（トークンをタブの中だけに置くため）。もう一度開くとログインの画面に移ります
- 運用者でないアカウント（配信元）でログインすると「配信元の画面は準備中です」と出ます

## 2. 画面の地図

| メニュー | できること |
|---|---|
| 概要 | 最新の公開と期限、署名鍵の状態をひと目で確かめる |
| 公開 | 公開の履歴を見る。今すぐ作り直す |
| 署名鍵・鍵セット | KMS の鍵を署名鍵として登録する。鍵セットの入力を作り、ルート鍵で署名した鍵セットを登録する |
| 配信元 | 配信元の一覧・詳細、停止・再開、上限の変更、その配信元のチャンネル |
| チャンネル | チャンネル ID で探して状態を見る。取り下げる |
| 操作の記録 | 月ごと、または対象（配信元・チャンネルなど）ごとに記録を見る |

状態を変える操作には、すべて「理由」を入れます。理由は操作の記録に残り、取り下げの理由はアプリの利用者にも見せます。

## 3. 日々の確認

「概要」で次を見ます。

| 項目 | 正常 | 気にすること |
|---|---|---|
| 最新の公開 | 毎日 03:00 ごろの `daily`、または操作のたびに増えている | 2 日以上増えていない |
| 期限 | 発行から 14 日後 | **あと 3 日を切ると赤字で警告**。毎日の作り直しが止まっている。「公開」で作り直しを試し、だめなら開発・保守の担当者へ |
| 署名鍵 | 使っている鍵が `active`、期限まで 1 か月以上 | 期限が近い → [署名鍵の入れ替え](#53-署名鍵の入れ替え半年ごと) |

## 4. 公開

承認・取り下げ・鍵セットの登録のたびと、毎日 03:00 に、リストは自動で作り直されます。ふだん手で公開する必要はありません。

**今すぐ作り直す**: 「公開」で理由を入れて「今すぐ作り直す」を押します。数秒後に履歴へ新しい `seq` が増えます（きっかけ「手動」）。増えないときは [困ったとき](#12-困ったとき)。

履歴の各行は、`seq`、公開の日時、期限、きっかけ（承認・取り下げ・鍵の移し替え・鍵セット・毎日・手動）、載せたチャンネルと取り下げの数、署名した鍵、リスト本体の SHA-256 です。

## 5. 署名鍵と鍵セット

### 5.1 しくみ

- **署名鍵**は KMS の中にあり、取り出せません。開発・保守の担当者が作ります（CDK の設定に鍵 ID を足して配備）
- **鍵セット**は「どの署名鍵を、いつからいつまで使ってよいか」の一覧で、**ルート鍵**がオフラインで署名します。ルート鍵はこのシステムに入れません
- 公開の処理は、鍵セットに載っていて、期間内で、状態が `active` の鍵で署名します

| 署名鍵の状態 | 意味 |
|---|---|
| `registered` | 登録したが、まだ鍵セットに載っていない（署名に使わない） |
| `active` | 今の鍵セットに載っている（署名に使う） |
| `retiring` | 前の鍵セットにはあったが、今の鍵セットにはない |
| `revoked` | 鍵セットで失効させた。二度と使わない |

### 5.2 鍵セットを登録する

1. 「署名鍵・鍵セット」の表で、鍵セットに入れる署名鍵にチェックを入れます
2. 有効期間（日、366 以下。既定は 180）を決めます
3. 表示された JSON を「コピー」し、USB メモリなどでルート鍵のある**オフラインの端末**に写します（ファイル名 `keyset-input.json`）
4. オフラインの端末で署名します（合言葉は環境変数で渡す）

   ```sh
   ROOT_KEY_PASSPHRASE=… sanpo-root-key sign-keyset --root-key root-key.pem --in keyset-input.json --out keyset.json
   ```

   署名の前に、鍵 ID の重なり、有効期間（1 年以内）、公開鍵の形を確かめます。問題があれば署名しません
5. できた `keyset.json` を運用者の端末に戻し、中身を「署名した鍵セットを登録する」に貼り付けて登録します
6. 登録すると、載せた鍵が `active` になり、リストが作り直されます

登録が拒まれる主な理由: ルート鍵の署名でない（`invalid_signature`）、`seq` が今のもの以下、載せた鍵が未登録、または KMS の公開鍵と違う（`keyset_invalid`）。

### 5.3 署名鍵の入れ替え（半年ごと）

署名鍵は半年ごとに入れ替えます（ADR-001 A-8）。新旧の鍵を一時的に両方載せるので、アプリが止まることはありません。

1. 開発・保守の担当者に、新しい鍵 ID（例 `k-2027-04`）の KMS の鍵を作ってもらい、ARN を受け取る
2. 「KMS の鍵を登録する」に鍵 ID と ARN を入れて登録する（`registered`）
3. 新旧の両方にチェックを入れて鍵セットを作り、署名して登録する（両方 `active`）
4. 数日たったら、新しい鍵だけにチェックを入れて鍵セットを作り、署名して登録する（古い鍵は `retiring`）

### 5.4 署名鍵を失効させる

署名鍵が漏れた疑いがあるとき（管理システムが乗っ取られた疑いを含む）は、[緊急時の対応](#11-緊急時の対応)のとおり、新しい署名鍵を用意したうえで、古い鍵 ID を `revokedKeys` に入れた鍵セットを作ります。画面が作る入力の `revokedKeys` には、今の鍵セットの失効の一覧が入っています。失効させる鍵 ID を、署名の前に手で足してください。失効させた鍵で署名されたリストは、アプリが署名の日時にかかわらず使いません。

## 6. 配信元の管理

「配信元」では、状態で絞り込んで一覧を見られます。詳細では、連絡先、アカウントID、今日の申請・試用チケットの数、チャンネルを見られます。

| 操作 | どうなるか |
|---|---|
| **停止する** | 申請と鍵の紐づけを受け付けなくなる（試用チケットも、3b で作ったら同じ）。**公開中のチャンネルはそのまま**残る。止めたいときは、別にチャンネルを取り下げる |
| **停止を解く** | 鍵を紐づけ済みなら `active`、まだなら `pending_key` に戻る |
| **上限を変える** | チャンネル数、1 日の申請、1 日の試用チケットを、その配信元だけ変える（0〜1000）。空欄にして保存すると既定値（5・20・10）に戻る |

## 7. チャンネルの取り下げ

承認したチャンネルに審査基準に反することが分かったら取り下げます（審査基準「取り下げ」）。

1. 「チャンネル」でチャンネル ID を入れて表示する
2. 重さを選ぶ
   - **重い**: 安全を損なう誘い、違法な内容、個人情報の収集、権利侵害 → すぐに取り下げる
   - **軽い**: 事実の小さな誤り、説明と内容のずれ → 先に配信元へ修正を求め、期限までに直らなければ取り下げる
3. 取り下げる版を入れる（空欄はすべての版）
4. **利用者に見せる理由**を入れて「取り下げる」

取り下げると、チャンネルはリストから消え、`revoked` に理由とともに 7 日載ります。アプリはパッケージを消して、利用者に理由を知らせます。**元に戻すには新しい版の承認が要ります**（前の版には自動で戻りません）。

## 8. 審査

🚧 **予定**: まだ使えません。

実装の順番 3 で作ります。予定の流れは次のとおりです（API-001、審査基準）。

1. 「審査待ち」の一覧（古い順）から申請を選び、審査を始める
2. 機械の確認の結果と、パッケージ・アイコンの中身を確かめる
3. 審査基準 2.7 の場面（散歩の開始、スポットの解説、再訪、休憩、区切り、終了）のプロンプトを使い、**運用者の AI の API キーでブラウザから** AI に話させて見本を作る。キーはサーバーに送らない。2 つ以上の AI サービスで試す
4. 審査基準の項目（2.1 語り口と内容、2.2 安全、2.3 プライバシー、2.4 宣伝、2.5 AI への指示、2.6 素材ときっかけ、2.7 見本）で確かめる
5. 承認・差し戻し・却下を決める。差し戻し・却下は、審査基準の項目番号つきの理由を 1 つ以上入れる。配信元にメールで知らせる

## 9. 配信元の鍵の移し替え

🚧 **予定**: まだ使えません。

配信元が鍵をなくした・漏れたときの救済です（ADR-001 D-3）。予定の流れ:

1. 配信元が新しい鍵を紐づけ、移し替えを申し出る
2. 運用者が「移し替えの申し出」の一覧から開き、**鍵とは別の経路**（登録済みの連絡先など）で本人確認する。確認の方法と内容を記録に入れる
3. 承認すると、配信元のすべてのチャンネルが新しい鍵に移り、古い鍵の署名の審査待ちの申請は差し戻される。リストには移し替えが 90 日示され、アプリは利用者に一度知らせる

## 10. 操作の記録

「操作の記録」では、月ごと、または対象ごとに記録を見られます。記録は消しません。

| 対象の書き方 | 例 |
|---|---|
| 配信元 | `PUB#01J…`（配信元の詳細の下のリンクから開ける） |
| チャンネル | `CH#kamakura-history` |
| 鍵セット・署名鍵・公開 | `KEYSET`、`SIGNKEY#k-2026-10`、`PUBLICATION` |

主な操作の名前: `publisher.suspend`・`publisher.resume`・`limits.update`・`channel.revoke`・`signing-key.register`・`keyset.register`・`publication.request`。

## 11. 緊急時の対応

| 事態 | すること |
|---|---|
| 不適切なチャンネルが公開されている | [取り下げ](#7-チャンネルの取り下げ)（重い）。必要なら配信元を停止する |
| 配信元が悪用している | 配信元を停止し、公開中のチャンネルを取り下げる |
| 署名鍵の漏えい・管理システムの乗っ取りの疑い | 開発・保守の担当者に新しい署名鍵を作ってもらい、新しい鍵を登録して、古い鍵を `revokedKeys` に入れた鍵セットに署名して登録する。ルート鍵は管理システムの外にあるので、これで立て直せる。アプリに届くまで最大 24 時間 |
| ルート鍵をなくした | 鍵セットを作れなくなる。開発用はルート鍵から作り直す。本番は新しい提供元になり、アプリの更新が要る。**ルート鍵の写しは必ず複数の場所に置く** |
| リストの期限が近い（概要で警告） | 「公開」で作り直す。失敗するなら開発・保守の担当者へ（警報のメールの宛先を設定していれば、警報も届く。開発用は未設定） |

## 12. 困ったとき

| 画面の表示 | 意味と対処 |
|---|---|
| ほかの人が先に変更しました | 開いている間に、ほかの人（または別のタブ）が同じものを変えた（`precondition_failed`）。読み込み直し、内容を確かめてからやり直す |
| 今の状態ではこの操作はできません | 例: 停止中の配信元をもう一度停止した、取り下げ済みのチャンネルを取り下げた（`invalid_state`） |
| この操作をする権限がありません | 運用者のグループに入っていない（`forbidden`） |
| 操作が多すぎます | 短い間に操作しすぎた（毎秒 20 回まで）。少し待つ |
| 鍵セットが正しくありません／署名が正しくありません | [5.2](#52-鍵セットを登録する) の拒まれる理由を見る |
| サーバーで問題が起きました | 表示された `instance`（要求 ID）を添えて、開発・保守の担当者へ |
| 手動の公開をしても履歴が増えない | 公開の処理が失敗している。開発・保守の担当者へ（CloudWatch の警報 `PublishFailures` が鳴っている） |
| ログインの画面から進まない | 認証アプリのコードの時刻ずれ、または MFA の端末をなくした。開発・保守の担当者へ |
